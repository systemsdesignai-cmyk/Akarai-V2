# Akarai — Prototype PRD v1.1
23 November 2026 | Status: proposed implementation baseline, approved strategy retained

## 1. Objective and scope
Deliver a complete, demonstrable, mobile-first property management PWA for South African independent landlords, initially Habesha communities. Primary segment 6–30 rental units; secondary 1–5. Financial control is the primary value; administrative efficiency and accountability secondary. Market demand and pricing remain hypotheses. Prototype success means a landlord can complete realistic end-to-end workflows using synthetic data, with accurate persistent local records, without relying on a backend. No live payment processing, real authentication, cloud synchronization or real tenant data in this checkpoint. Later: secure cloud sync (Supabase provisional), freemium unit-based plans, hybrid subscription payment, PWA then Android then iOS.

## 4. Financial and data invariants
Use integer cents; reject non-finite, invalid or negative payment amounts unless explicit reversal/adjustment workflow. Use atomic transactions for financial events and receipts; stable idempotency keys; prevent double-submit and duplicate recurring charges. Preserve immutable posted history and traceable corrections. Derive balances from authoritative ledger, not unrelated UI counters. Define allocation, credit, deposit, occupancy and reporting rules in code and tests. Test boundary dates, rounding, empty data, multiple properties and reversal. No automatic deletion of existing data on startup, update or role switch. Initialization failure must show recoverable error, not silently continue. Backup/restore must validate schema and references before atomic mutation. Synthetic datasets only; local storage is not a secure multi-user boundary.

## 5. UX and ethical behavioral design
Mobile-first 360–430px and responsive tablet/desktop; accessible contrast, readable typography, keyboard navigation, focus, reduced motion, touch targets ~44px, no clipping or layout shifts. Preserve brand and information architecture. Use progressive disclosure, familiar labels, editable defaults, recent selections, contextual shortcuts, inline validation and immediate feedback. Goal-gradient: actual monthly collection progress, not arbitrary points. Endowed progress: truthful onboarding checklist. Salience/loss aversion: actual overdue amounts and due dates, neutral language, no invented urgency. Implementation intentions: user-selected follow-up date and action; local reminders only where technically supported, otherwise in-app due list. Zeigarnik: resumable incomplete tasks without pressure. Self-efficacy: factual month-over-month insights where comparable data exists. Habit loop: due task → quick action → confirmation → updated ledger → next useful action. No streak penalties, fake scarcity, forced notifications, hidden fees or engagement for its own sake. Allow dismiss/undo where safe; financial corrections use reversals. Target fewer steps and fewer errors, not time spent. Proposed usability targets: record a known tenant payment within 30 seconds, find outstanding balance within 10 seconds, complete setup without assistance; measure with testers, do not claim achieved.

## 6. Verification and release gates
Inventory every route, button, modal, form and external integration. Classify functional local, simulated, external handoff, blocked or broken. Test fresh install, existing data migration, reload, offline, backup restore, mobile/desktop, language/theme, empty/error states, rapid double-click, financial reconciliation and demo/clean separation. Use existing lockfile, run typecheck/build and focused automated tests if environment permits. Record commands, results and evidence; PASS/FAIL/NOT RUN. No unsupported claims. Test GitHub Pages base /Akeray-LandLordOS/, asset paths, service worker scope and nested route fallback. Preserve deployment workflow; do not deploy or merge without user approval. Prototype release requires no known critical local data loss or financial integrity defect; unresolved failures explicitly disclosed. Real-user beta with personal data requires separate production security and POPIA review.

## 7. Deferred production scope
Secure authentication, server-enforced tenant isolation, cloud sync and conflict protocol, encrypted/controlled cloud documents, payment provider and subscription enforcement, automated WhatsApp/SMS/push, production monitoring, compliance and store packaging. Simulate only with clear labels and never collect real credentials or payment details. Pricing, payment providers and language quality require validation. This PRD proposes acceptance targets and UX refinements, not evidence of existing functionality or market demand.
